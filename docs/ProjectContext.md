## 对话摘要日志

### 2026-04-01

- 聊天页自动滚动当前又补了一条高可感知的交互修复：当用户发送第一条超长消息时，消息区不应该因为内容瞬间撑高就误以为“用户已经离开底部”。
- 当前根因已经明确：之前自动滚动逻辑主要靠“当前是否接近底部”即时推断 follow 状态，而首条长消息会在发送链路里先把内容撑高、再触发滚动，从而把 follow 误关掉；一旦 follow 被误关，assistant 开始流式回复后也不会继续自动跟随。
- 因此当前自动滚动策略已经从“只靠当前位置推断”补成了“发送期间显式 follow lock + 用户主动上滑才退出”的语义。
- 与此同时，自动滚动的 Web 回归输入当前也已经进一步贴近真实用户的“整份简历首消息”场景，不再只用压缩版长文本，而是覆盖更完整的个人优势、工作经历和多项目内容，避免测试样本过短导致的假稳定。
- 这条修复的产品边界也已经明确：
  - 用户刚主动发送消息后，系统应持续跟随到底部
  - 只有检测到用户真的上滑，才停止跟随
  - 不能因为一条超长消息本身把内容撑高，就误判成用户主动离开底部
- 当前真实 Web 回归也已补上超长首消息场景，直接检查滚动容器距离底部的距离，而不是只看按钮显隐。

- 模拟面试首轮“用户直接发来整份简历并要求开始面试”的场景，当前产品语义已经进一步收紧：
  - 第一条 assistant 回复应该先用 1 到 2 句简短自然的话承接简历，再直接进入 `第一个问题`
  - 如果内部计划里没有 feedback，模型不应该自行补一段 `**点评**：` 去评价简历
- 同时，用户对可见格式的要求也已经进一步明确：`**点评**：` 和 `**第X个问题：**` 这两个标签都必须与正文写在同一行，不能再单独换行。
- 这层格式要求现在又进一步补细了一条：如果主问题后面还有 `（提示）`，这段提示必须保留，并且独占一行展示，不能被模型省略，也不能贴在题干后面。
- 因此当前不仅继续调整了引擎开场题面，也把这两个约束下沉到了真实流式 prompt 和 reply shape instruction 里；也就是说，这不再只是 few-shot 风格偏好，而是明确的输出协议。
- mock / fallback 链路当前也同步收成相同格式，避免真实模型修好了，但测试链路或降级链路仍然露出旧的两行式题面。

- 模拟面试的真实回复格式当前已经不再只靠 few-shot 学习，而是开始显式约束段落结构和题号规则。
- 当前产品判断进一步明确了：像“点评是否单独成段”“第 X 个问题是否粗体”“追问时能不能重新开号”这类问题，不适合继续只靠模型自己悟，因为它们本质是高约束格式问题。
- 因此当前在真实流式 prompt 里已经显式补上两层硬规则：
  - 新主问题优先按“承接 -> **点评** -> **第X个问题：** -> （提示）”输出
  - 追问禁止重新编号；如果内部计划已经给出 `第二个问题` 之类题号，模型输出必须原样保留，不能重置成 `第一个问题`
- 与此同时，开场首题的引擎本地题面也同步收口，去掉了“我当前对你的理解是”这类系统分析句，避免首轮就把模型往错误格式上带。

- 当前这一步的产品意义也很明确：真人面试官问事件循环和问商品列表页方案，不会用同一套追问口吻；前者应该追机制和边界，后者应该追方案拆解和边界条件，而工程实践题则更应该追工具链取舍、落地约束和迁移成本。
- 与此同时，mock provider 和真实模型 few-shot 当前也已同步接入这层技术题语义；这样即使在 mock、fallback 或 stop 场景里，技术题也不该再退化成统一模板。

  - 经历主线
  - 代表项目
  - 求职动机
- 这次收口继续坚持低侵入原则，没有为 warmup 追问新增数据库字段，而是直接复用现有 `followUpTrace / followUpRound / activeQuestionAnswers`，只把开场首题补成一个 runtime 虚拟问题。
- 当前产品语义也更明确了：如果候选人的开场回答已经足够完整，就应该自然进入技术题；如果回答还比较虚，就应该先在开场阶段追一两个关键点，而不是无条件切下一题。
- 与此同时，mock provider 和真实模型的 few-shot 当前也已同步接入 warmup 追问语义；这样即使在 mock、fallback 或 stop 场景里，开场追问也不该再退化成技术题式的统一模板口吻。

  - 加载性能项目
  - 渲染性能项目
  - 构建性能项目
- 这次收口仍然坚持低侵入原则，没有为“性能子类型”新增数据库字段，而是继续复用 `ResumeProfile` 的 `primaryTags / projectTags / strengths / evidence` 和用户输入文本做轻量推断。
- 同时，为了减少“构建优化”被误判成纯工程化项目的情况，当前在运行时新增了一层轻量的性能语义加权：如果文本里同时出现构建链路词和明显的优化收益词，会优先进入性能项目分支，再在内部细分成构建性能问法。
- 当前这一步的产品意义很明确：同样都是“性能项目”，真人面试官不会用一套题追完所有人；做首屏优化的人，应该被追指标和资源加载链路，做渲染治理的人，应该被追卡顿与无效渲染，做构建提速的人，则应该被追编译器取舍、兼容性风险和研发效率收益闭环。

- 当前至少区分三类项目主问题：
  - 工程化 / 基础设施项目
  - 性能优化项目
  - 业务交付项目
- 这次收口依然坚持低侵入原则：没有为“项目类型”新增数据库字段，而是直接复用 `ResumeProfile` 现有的 `primaryTags / projectTags / strengths / evidence` 做轻量推断。
- 同时，用户可见文案里的 canonical tag 当前也已开始做显示层翻译；像 `engineering` 这类内部标签，不应该再直接出现在 warmup 或项目深挖题面里。

- 模拟面试里的项目深挖追问当前已经不再只有一种泛化口吻，而是开始根据缺失点自动切换焦点。
- 当前至少已区分三类项目追问：
  - 追背景复杂度 / 职责边界
  - 追方案取舍 / 权衡
  - 追结果验证 / 收益闭环
- 这次收口的关键工程判断是：不需要为此新增数据库字段或重写状态机，因为现有 `followUpTrace.askedMissingPoint` 和项目题 `keyPoints` 已经足够提供分类信号。
- 当前真实模型的面试 prompt 和 mock provider 的项目追问文案也已经开始共用这套产品语义；这样一来，即使在 mock、stop 或 fallback 场景里，项目追问也不会再显得像同一条模板换皮。

- 模拟面试这条线当前又进一步收口了两个很具体、但用户能立刻感知到的“假感”来源：
  - 题目标题里的 topic 标签，例如 `第 2 个问题（engineering）`
  - 项目深挖题面里的模板术语，例如“按 STAR 的思路讲清楚”
- 当前产品判断已经很明确：这些信息即使在内部有价值，也不应该直接出现在用户可见文案里；尤其 stop / fallback / mock 场景最容易暴露底层实现痕迹，所以这类文案要优先清理。
- 因此当前 mock provider 的题目文案已经统一收口为更自然的 `第 N 个问题：`，项目深挖题面也改成“你可以按这条主线来讲”，保留结构感，但不再像模板训练器。
- 项目深挖追问的 mock 口吻当前也开始和技术题分开：项目题更强调“背景、动作、取舍、收益验证”，而不是继续沿用技术机制题的追问语气。

- 模拟面试这条线当前又往“阶段更清楚、口吻更像真人”推进了一步：给真实模型的面试 prompt 已不再只传“这轮计划片段”，而是开始显式传“当前面试阶段”。
- 当前已经至少区分：
  - 开场破冰
  - 技术题
  - 项目深挖
  - 总结收口
- 这一步的价值不在于多加几个标签，而在于让模型能根据阶段自动切换问法：
  - 技术题更像原理或场景追问
  - 项目深挖更像项目复盘与方案取舍追问
  - 总结阶段更像自然收口而不是继续出题
- 与此同时，面试内部 `system` 规划片段当前也已从用户可见草案里过滤掉；这意味着即使发生 mock 回放、早停或真实流式还没吐出内容就被中止，页面上也不该再看到“已根据你的输入生成本场面试计划”这种内部播报。
- 当前这条收口的产品含义很明确：内部规划仍然可以帮助状态机和真实模型协作，但内部规划不应该作为用户可见文案的一部分存在。

- 模拟面试这条线当前又往“更像真人面试官现场说话”推进了一步：用户可见回复虽然仍由 `interview-engine` 决定追问/切题/收口时机，但给真实模型的面试专用 prompt 现在已经开始按回合类型注入 few-shot，而不是只靠一组静态规则。
- 当前至少已经区分四类说话方式：
  - 点评后进入下一道主问题
  - 点评后继续追问
  - 总结收口
  - 点评后继续推进
- 这次收口的产品判断很明确：如果继续把“自然度”建立在本地规则拼接上，面试体验会越来越像脚本；更合理的做法是保留状态机负责节奏，把“怎么说得自然”交给真实模型从 few-shot 中学习。
- 与此同时，面试专用的 mock 快捷流当前也已和普通 mock provider 共用同一套 `MOCK_STREAM_DELTA_DELAY_MS` 节奏控制；这一步不是为了产品功能，而是为了让“停止生成”类 Playwright 回归真正测到稳定的中止语义，而不是继续和几十毫秒级的快捷流抢时机。
- 这也意味着后续凡是新增面试 stop / partial / 中断持久化相关回归时，应优先复用统一的 mock 分片延迟配置，而不要再在单条用例里堆额外等待。

- 模拟面试这条主链当前正式开始从“统一 questionPlan 顺排执行”往“阶段式面试流程”收口；这次不是推翻已有规划、评分和报告骨架，而是在执行层先落首版 `warmup -> technical -> project -> wrap_up`。
- 这次收口的核心产品判断很明确：用户对“像真实面试”的感知，主要不取决于题库数量，而取决于是否有开场破冰、是否会在技术题后自然过渡到项目深挖、以及整场面试是否像人在控节奏。
- 因此当前新的执行语义已经不是“开始模拟面试后立即进入第一道技术题”，而是：
  - 先基于画像做一轮开场自我介绍题
  - 再进入题单驱动的技术题阶段
  - 若用户提供了较完整的背景信息，再补一轮项目深挖
  - 最后统一收束到报告
- 这一步的工程价值在于：继续保留现有 `ResumeProfile / InterviewBlueprint / planningTrace / assessmentTrace / reportTrace` 这些已经搭好的骨架，不新增表、不改接口，只在 runtime JSON 里补 `currentStage / projectQuestion` 两个阶段执行字段，就把面试体验往“真实流程”推进了一档。
- 阶段式面试当前也已经补上一条真实 Web Playwright 回归：测试会创建一个 `questionCount = 1` 的会话配置，然后验证整条用户可见链路会按 `warmup -> technical -> project` 依次推进，而不是在页面上只停留在第一道技术题。
- 当前也明确没有一步到位做全量 Agent 化执行图；短期优先做的是“先把用户真正能感知到的面试流程做对”，后续再把行为面、算法题、HR 面、跳题策略和更细的项目追问继续拆进阶段状态机或 LangGraph 子图。

  - 注入改成按父文档顺序组织，保证流程完整性
  - trace 继续保留真实排序结果，避免为了生成稳定性牺牲排障能力
- 这意味着后续像“面试流程”“HR 面会聊什么”“offer 阶段怎么谈”这类问题，不应再通过无止境调 `TopK` 来补救，而应继续沿着“流程文档按顺序展开”的策略演进。

- 这组评测当前刻意保持为确定性、可进 CI 的实现，不依赖真实模型：
  - 检索层检查 Top1 / TopK / 分数阈值 / 排除项
  - 回答层检查关键事实覆盖、禁用结论以及相对 baseline 的覆盖增益
- 当前这个设计的工程取向很明确：先把评测 fixture、执行器和样例结构稳定下来，再视需要逐步叠加 LLM judge，而不是一开始就把“回答关联度评测”完全建立在会波动的模型判分上。

- 项目级协作约定现已继续收口：凡是涉及 Web/Admin 交互、聊天链路、流式输出或其他用户可见流程的改动，交付前除了 `pnpm verify` 之外，还要求额外做至少一轮 Playwright 自测。
- 当前推荐顺序是：
  - 若仓库中已有对应 E2E，用现成 Playwright 用例直接回归；
  - 若还没有对应自动化用例，则至少用 Playwright 浏览器做一轮手动验证，并在交付说明里写明验证路径与结果。
- 这样收口的目的不是增加流程负担，而是避免“代码和单测都过了，但真实交互链路仍有断点”这类前端/全栈项目里最常见的回归。
- 为了减少每次交付前重新查命令，`AGENTS.md` 当前还新增了一组固定的 Playwright 自测命令模板，包含：
  - `pnpm test:e2e:web`
  - `pnpm test:e2e:admin`
  - `PLAYWRIGHT_SCOPE=web pnpm test:e2e:web --grep '<关键字>'`
  - `PLAYWRIGHT_SCOPE=admin pnpm test:e2e:admin --grep '<关键字>'`
  - `PLAYWRIGHT_SKIP_WEBSERVER=1 ...`
- 当前建议的执行策略也已写清：能精确命中改动面的优先跑 `--grep`，影响范围较大时再跑对应端全量 E2E；若本地已有手动启动服务，可显式加 `PLAYWRIGHT_SKIP_WEBSERVER=1` 避免端口冲突。

- 文档知识增强的产品口径现已继续收口为“默认隐式增强，而不是显式自报来源”：知识文档仍会进入 system context，但系统提示已明确要求模型不要在正文里主动说“根据某文档/资料/知识库”，也不要直接报出文档标题。
- 当前更推荐的产品表现是“像资深面试官本来就懂这些知识一样自然回答”；只有当用户明确追问依据、来源或参考材料时，才允许模型再概括说明来源。
- 为了降低模型自曝实现细节的倾向，知识注入 prompt 的包装文案也已从“参考资料 / 文档标题 / 来源分类”收口为更中性的“内部知识背景 / 知识主题 / 背景分类”；这次收口不改变检索逻辑，只调整回答时的角色呈现方式。

- 文档知识库这条 MVP 链路现已补上一条稳定的 Web Playwright 防回归：测试会直接种入一篇已发布知识文档，再通过 Web 真实 `/api/chat/sessions/*/messages/stream` 发起技术问题，断言 mock provider 的回复中出现知识命中文档标题。
- 这条 E2E 不依赖真实外部模型，而是通过测试专用 mock provider 回显“知识命中：文档标题”来验证“检索命中 -> prompt 注入 -> 流式回复”整条链路已经打通；当前这是更适合 MVP 阶段的工程化方案，因为它稳定、可进 CI、能明确防回归。
- 为了让这条回归尽量低侵入，mock provider 当前只在 `MOCK_STREAM_ECHO_KNOWLEDGE=1` 的测试环境下才会回显知识命中信息；正常开发和真实模型链路不会暴露这类测试信号。

- 为了让面试通这类强领域产品在 MVP 阶段先快速建立“前端领域感”，知识增强方案已明确收口为“后台文档管理 + 定向检索增强”，而不是一开始就上重型知识中台。
- 当前新增的知识库能力只服务三类资料：
  - `tech_knowledge`：前端技术知识
  - `interview_playbook`：面试话术、回答框架、常见追问打法
  - `project_resume`：项目亮点、简历项目素材、可复用表述
- 后台新增 `Documents` 模块后，管理员可以直接录入或维护 Markdown 文档；服务端会在保存时按 Markdown 标题自动分 section，并进一步切成适合检索的 chunk，保留标题路径、标签和搜索文本。
- 这套知识增强当前故意不做 PDF/Word 解析、不做 embedding/向量库、不做复杂审核流，也不对所有聊天请求默认检索；核心目标是先用最少工程复杂度，把“普通聊天里的领域命中率”显著拉起来。
- 普通聊天链路现已按意图选择性接入知识检索：
  - `technical_question` 优先检索 `tech_knowledge + interview_playbook`
  - `project_highlight / resume_optimize` 优先检索 `project_resume + interview_playbook`
  - `self_intro` 优先检索 `interview_playbook + project_resume`
- 检索命中策略也已明确分层：
  - 强命中：把资料作为高优先级依据注入 prompt，要求回答优先参考资料，但不能捏造资料中没有的事实
  - 弱命中：只把资料作为辅助背景，允许模型自行判断是否引用，避免“低相关资料被强行套用”
  - 未命中：不注入任何资料，直接回落到现有通用 system prompt、意图策略和 few-shot，模型仍能正常回答，只是不额外获得后台文档的增强
- 当前检索实现使用“词法召回 + 标题路径加权 + 标签命中加权”的轻量方案，已把检索层从上层聊天策略里独立出来；若后续资料规模继续上涨，再把 `KnowledgeDocumentChunk` 平滑升级为 `pgvector + embeddings` 即可，不需要推翻现有后台和 prompt 拼接边界。

- 普通聊天里“技术问答”的回答深度策略已继续收口：当前不再满足于“只有结构、但讲得偏短”的最小回答，而是明确要求在用户未指定“简短回答”时，默认按“中等偏详细”深度展开。
- 这次收口不会把所有普通聊天都一起拉长；闲聊、问候语、简单算术等轻场景仍保持轻量，当前产品策略是“只提升 `technical_question` 的默认展开深度，不改意图识别边界”。
- 技术问答 prompt 的重点约束也已同步调整为：首段结论后要补核心原因，各主要小节尽量补“为什么 / 什么时候 / 边界条件 / 常见误用”，示例允许给到 `1~2` 个最小示例或业务场景，而不再只鼓励一句提纲式短示例。
- 为避免模型继续模仿旧的短答风格，comparison / mechanism / concept 三类技术问答的 few-shot 与 fallback 也已同步拉长一档，当前目标是让回答更像“资深前端面试官讲清楚问题”，而不是只给最短模板骨架。

- Web 聊天里的消息编辑交互已再次收口为“确定即重生成”：当前对齐既定产品基线，不再因为“输入全空白”或“内容与原消息等价”而阻止提交；只要用户点击编辑里的“确定”，都会触发一轮新的 assistant 生成。
- 为兼顾现有服务端接口仍要求 `content` 非空的约束，前端当前采用的具体策略是：
  - 若编辑后内容 `trim()` 为空，则沿用原消息内容重生成
  - 若编辑后内容与原消息 `trim()` 后等价，也沿用原消息内容重生成
  - 只有存在实质改动时，才把新的文本作为编辑结果提交
- 先前那套“编辑内容不能为空”的前端局部错误提示、`editingError` 状态和对应 `aria-invalid / aria-describedby` 关联，当前已从主链路移除；这不是可访问性退化，而是产品语义显式改成“不拦截，直接重生成”。
- 为保持这套语义简单一致，编辑后 assistant 中断消息上的“恢复原回复”入口也已移除；当前不会再为单次编辑重生成维护额外的回复回退版本。

- Web 聊天页的消息编辑产品逻辑现已再次收口：当前对齐豆包等产品，只允许编辑“最后一条用户消息”，非最后一条消息不再展示编辑按钮。
- 这次收口的核心原因不是技术上做不到历史消息编辑，而是当前主链会话语义下，编辑历史消息会立刻引出“后续消息是否继续有效”的产品分歧；在未引入“分支会话 / 版本快照”前，先禁止历史消息编辑是更稳的 MVP 策略。
- 前端当前除了在消息动作区隐藏非最后一条用户消息的编辑按钮，也会在真正提交前再次校验“是否仍为最后一条用户消息”；但对空白/等价编辑已不再拦截，而是继续发起重生成。

- Web 端普通聊天的“停止生成”语义又往前收口了一步：如果 assistant 已经输出了部分内容，当前不会只在前端临时保留，而是会把这条 assistant 作为 `completionStatus = interrupted` 的正式消息持久化；聊天页和 Admin 都会显示“已停止生成”状态。
- 同一轮里，如果用户在 assistant 还没吐出任何内容时就点击停止，当前也会通过显式补写接口把“仅用户消息”的中断轮次持久化，避免刷新后这条已发送消息消失。
- 因为 `ChatSessionRecord.messages` 本身就是 JSONB，本次只是在消息对象里增加可选 `completionStatus` 字段，不需要新增 Prisma 列或做数据库 migration。
- 为避免“用户点击停止后的补写请求”和原 SSE 路由自己的收尾逻辑同时落库造成重复消息，当前中断补写链路会携带 `expectedMessageCount` 做并发保护；如果远端已先推进，则直接采用远端结果。
- Playwright 真实回归里还额外暴露了一条服务端稳态问题：用户中止后 `ReadableStream` 控制器可能已提前关闭，之前继续 `enqueue error/end` 会报 `Controller is already closed`；这条异常现在已统一通过安全 `enqueue / finalize` helper 收口，避免污染日志。

- Web 端普通聊天对“终止生成”的交互语义也已明确收口：当用户在 assistant 流式输出过程中点击停止时，本轮用户消息必须保留，因为它已经发出；当前只会取消 assistant 继续生成，并在本地收口空的 assistant 占位或保留已生成的部分内容。
- 这条链路还额外修掉了一个更隐蔽的竞态：如果当前会话本来就已存在于服务端，停止后前端再去拉取远端旧会话，之前会把刚发出的本轮用户消息覆盖掉；现在会先判断远端是否真的推进，只有远端已落库时才采用远端结果，否则保留本地中止态。
- Web 端普通聊天的角色口径也做了一轮统一：当前全局 system prompt 已从“面试通的 AI 助手”收口为“面试通，一个互联网大公司的资深程序员和面试官，专注于前端技术领域”，并同步覆盖问候语示例与 fallback，自我身份不再在不同入口间摇摆。
- Web 端普通聊天的格式约束又做了一轮收口：当前已移除“不要使用 Markdown 分割线”和“不要输出 mermaid 图”这两条系统提示限制。
- assistant 回复的服务端 Markdown 规范化也已同步放开：现在不会再清洗普通文本中的 Markdown 分割线，因此模型若输出 `--- / *** / ___`，前端会按原样渲染；这次调整仍保留既有代码块补全、语言修正与不平衡 fence 清理逻辑。

- GitHub Actions 的 `web-e2e` 失败根因已定位清楚：不是 Playwright 断言本身不稳定，而是 Web 端当前已经接入游客 `UserActor`、会话持久化和额度逻辑，CI 中每次访问 `/api/chat/usage`、`/api/chat/sessions`、`/api/chat/sessions/[sessionId]/messages/stream` 都会触发 Prisma 访问数据库。
- 原 `web-e2e` job 仍沿用“只启动 Web + mock LLM、不带数据库”的旧配置，因此在 GitHub Actions 中稳定报 `Prisma P1001 Can't reach database server at 127.0.0.1:5432`，随后页面只停留在输入问题和 loading 状态，导致所有断言都看不到预期 assistant 文本。
- 当前结论已经收口为：`web-e2e` 必须与 `admin-e2e` 一样补齐 `pgvector` service、`DATABASE_URL` 和 `pnpm db:migrate:deploy`，否则这条链路不具备真实可运行前提。

- 聊天页骨架已按最新产品要求收口回严格的“三段式”结构：header 在顶部、footer 在底部承载输入区，中间消息区独立滚动；此前那套“浏览器整页滚动 + fixed footer 浮层”的实现已经撤回。

- 这次演进的产品意义很明确：Admin 侧的知识检索概览页不再依赖会话 JSON 扫描，而是直接读取独立 trace 记录，后续做跨会话统计、高频 query 聚合、回归候选筛选时，不需要继续把分析逻辑绑死在 `runtime` 结构上。
- 当前切流方式刻意保持为“渐进式而非一次性迁移”：
  - `ChatSession.runtime.knowledgeRetrievalTrace` 仍兼容保留
  - Admin 概览页优先读新表
  - 历史 runtime trace 暂不回填到新表
- 高频 Query 与回归候选的聚合键当前也已从 `queryPreview` 文案本身收口到 `queryHash`，避免同一问题因措辞差异或长文截断被拆成多个统计桶。
- 这轮落地时还额外暴露出一个很典型的工程问题：Admin Playwright 之前默认复用本地 `3001` 上已存在的 Next dev server，导致测试可能命中旧 Prisma Client 进程，进而出现“新 model 在代码里存在、运行时却是 `undefined`”的假失败。
- 当前这个问题已经通过基础设施层收口：
  - Admin `next.config.ts` 支持 `NEXT_DIST_DIR`
  - Admin E2E 改用独立端口 `3101`
  - Playwright 不再复用已有 Admin dev server
- 这意味着后续只要 schema 变更后已正确 `db:generate`，Admin E2E 就不应该再因为复用陈旧开发进程而给出误导性的 Prisma 运行时错误。
- 在独立事件表切流之后，历史 `runtime.knowledgeRetrievalTrace` 当前也已经补上一条正式 backfill 路径：仓库根目录新增 `pnpm trace:knowledge:backfill`，会把旧 runtime 中仍有价值的 trace 幂等补写到新表。
- 这条 backfill 路径当前刻意保持保守兼容：
  - 旧 runtime 缺少 `triggerKind` 时，统一按 `new_message` 回填
  - 旧 runtime 缺少 `queryHash` 时，会退化为基于 `queryPreview` 生成 hash
- 这样做的取向很明确：先把历史样本尽量迁过去，让 Admin 概览页不至于只看到切流之后的新数据；但也明确承认旧 runtime 的观测粒度本来就低于现在的新表实时双写，不对历史数据做过度“伪精确”推断。
- 这条 backfill 路径当前又继续增强为更适合线上分批执行的版本：
  - 支持 `--created-after / --created-before`，按 trace 自身 `createdAt` 做窗口过滤
  - 支持 `--report-json` 输出结构化报告，便于 dry-run 留档和迁移审计
- 当前这个增强的工程取向也比较明确：优先保证“可以分批、可审计、可重复执行”，而不是把回填脚本做成一次性手工命令。
- 2026-04-01：模拟面试执行链路已从“直接顺排技术题”升级为首版阶段式流程：`warmup -> technical -> project -> wrap_up`。当前取舍非常明确：
  - 不推翻既有 `ResumeProfile / InterviewBlueprint / QuestionPlan / Report` 骨架
  - 先只重构执行层，让真实对话更像面试官而不是题库播放器
  - 项目深挖通过 runtime 中新增的 `currentStage / projectQuestion` 渐进接入，不做数据库迁移
- 2026-04-01：Web 端知识检索当前已确认存在一个真实工程约束：如果只靠 15 秒 TTL 缓存 `knowledgeDocumentChunk`，在后台更新已发布文档或并发 E2E 种子变动时，会让后续请求继续命中过期知识集。当前已收口为“TTL + 已发布文档数量 / 最新更新时间双校验”的失效策略，结论是：
  - 继续保留轻量内存缓存，避免每次都全量重建 searchable chunks
  - 但只要 published 文档有新增、删除或更新，就必须立刻失效缓存，不能把知识更新正确性让位给纯缓存命中率
- 2026-04-01：阶段式面试和多轮真实聊天的 Playwright 用例当前也已补上一条稳定性原则：E2E 不应假设“看到部分 assistant 文本就代表这一轮流式已经完成”。现在统一改为等待发送按钮恢复为“发送消息”后再进入下一轮或下一阶段断言，避免把流式时序抖动误判为业务回归。
- 2026-04-01：用户对模拟面试当前又给出了一条更明确的产品反馈：即使已经做成阶段式流程，如果一开场仍然播报“本场共几题 / 反馈模式”，整体体感依然像系统脚本，不像真人面试官。当前结论已经收敛为：
  - 启动面试后不要先讲规则，直接自然进入第一个问题
  - 问题对用户的展示方式统一改成“第一个问题 / 第二个问题 / 第七个问题”这类真人口吻，而不是 `问题 1/4`
  - 每道主问题在回答收口后都先给点评，再决定追问还是进入下一题
  - `feedbackMode` 暂时保留在配置层，但当前不再作为“是否展示逐题点评”的用户可见开关
- 2026-04-01：这也进一步明确了当前模拟面试链路的产品优先级。短期内，比“真 token 流式生成每一个字”更重要的是先把对话节奏做对：
  - 开场要像接住简历，而不是播报配置
  - 追问要像顺着回答往下压，而不是机械补题
  - 点评要像面试官复盘，而不是评分器出报表
  - 只有当这些节奏都自然了，再决定是否把 interview-engine 从“整条消息生成”继续升级到更强的流式生成体验
- 2026-04-01：这条后续路线现在已经正式往前推进了一步。当前模拟面试在 Web 流式路由里不再直接把 `interview-engine` 产出的整段文本原样返回给用户，而是改成：
  - `interview-engine` 仍负责状态推进、追问判定、评分和报告
  - 用户可见的提问 / 点评 / 追问文本，改由当前 `StreamChatProvider`（DeepSeek / Ollama）做真实 token 流式生成
  - 为了兼容现有前端协议，一次面试回合会先把内部多条 assistant 计划片段折叠成一条回复，再流式返回
- 2026-04-01：这次改法的关键产品取舍也已经明确：
  - 不做“本地草案按字切片”的假流式来冒充模型输出
  - 也不在这一轮重写整个面试状态机
  - 先采用“状态机保持可控、用户可见话术交给真实模型流式生成”的桥接方案，把体验和工程风险同时压在可接受范围内
- 2026-04-01：在这套桥接方案之上，面试 prompt 的上下文粒度当前又进一步收口了一步。当前结论是：不能只把“点评 / 下一题”的文本扔给模型，还要显式告诉它这轮到底是“继续追问”还是“进入下一道主问题”，以及它关联的是“第几个问题”。因此：
  - 面试追问消息现在已显式标记为 `follow_up`
  - 传给真实模型的 prompt 会额外带上：
    - `当前回合类型`
    - `当前关联主问题编号`
  - 这样模型在真实流式生成时，才更不容易把追问说成新题，或把下一题说成追问
- 2026-04-01：面试真实流式链路当前也已补上一条专门的 stop 回归。当前产品语义明确为：如果用户在面试官回复过程中点击停止，已经输出的 assistant 部分内容必须保留，并以中断态持久化；这条约束现在不再只靠通用聊天链路隐式继承，而是有独立的模拟面试 Web E2E 覆盖。
